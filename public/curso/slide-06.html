Cuatro capas: de la trama cruda al stored procedure

En las láminas anteriores vimos por dónde viaja una transacción. Ahora vamos a mirar el mensaje en sí: cómo se pasa de una norma genérica a los bytes que viajan por la red y, finalmente, a la lógica del banco. Para entenderlo, lo separamos en cuatro capas. CAPA 1 · El estándar ISO 8583 Es la estructura común, válida para cualquier implementación: • El MTI, que indica el tipo de mensaje. • El bitmap primario (y, si hace falta, el secundario), que indica qué campos vienen en la trama. • Los Data Elements, del DE1 al DE128, definidos de forma genérica. Pero el estándar no define el formato exacto: no dice en qué codificación viaja cada campo, cómo se expresa la longitud ni qué header de transporte se usa. El estándar da la gramática, pero todavía no el diccionario. CAPA 2 · El manual de la marca o del switch Visa, Mastercard, Amex, la procesadora o el host publican su propio manual, y es ahí donde se define el formato real: • Codificación: ASCII, BCD, EBCDIC o binario. • Unidad de longitud de los campos variables (LLVAR): si la longitud cuenta caracteres o bytes empaquetados. • Header de transporte: TPDU, length-prefix o un header propietario. CAPA 3 · La trama real que viaja Es lo que efectivamente se transmite: header de transporte + MTI + bitmap + Data Elements, con los bytes exactos que exige esa marca o switch. Una regla que conviene recordar: ante cualquier duda de formato, la fuente de verdad es el manual de la marca, no el estándar genérico. CAPA 4 · El switch o conector Es el componente que conoce las tres capas anteriores y hace de puente hacia el negocio: 1. Quita el header de transporte según el canal o la conexión. 2. Parsea el MTI, el bitmap y los campos aplicando las reglas del manual (codificación y longitud real). 3. Mapea cada campo decodificado a un parámetro de negocio: DE2 → @pan, DE4 → @monto, DE11 → @stan. 4. Invoca el stored procedure correspondiente (por ejemplo sp_compra o sp_transferencia) pasando esos parámetros. 5. El stored procedure ejecuta la lógica real: valida la cuenta, mueve el saldo y genera el movimiento, ya en el mundo del core bancario. En resumen: el estándar da la gramática, la marca describe el diccionario y el switch traduce todo a lógica de negocio. Esto es justamente lo que muestra el simulador: ATM + clientes + pasivas.
